# Правила разработки ECS

Применяй эти правила при добавлении, изменении и ревью компонентов, систем, событий и прототипов, которые подключают игровую механику.

## Компонент и система-владелец

- Для самостоятельной механики создай отдельный компонент и обслуживающую его систему. Добавляй компонент в прототипы конкретных сущностей, которым нужна эта возможность. Например, способность рюкзака автоматически заряжать оружие должна включаться на самом рюкзаке.
- Подписки вида `SubscribeLocalEvent<TComponent, TEvent>` размещай в системе, отвечающей за `TComponent`. Одна система может владеть несколькими связанными компонентами.
- Для взаимодействия механик определи предметное событие. Система-владелец обрабатывает исходное изменение и поднимает событие на подходящей сущности. Система-получатель подписывается на это событие через **свой** компонент. Например, система оружия сообщает о смене батареи, а система дозарядки решает, как это влияет на её кэш.

## Shared и сетевое состояние

- Размещай компоненты, события и логику в `Content.Shared`, когда это позволяют зависимости. В `Content.Server` и `Content.Client` выноси части, которым нужны API соответствующей стороны.
- В Shared-системе регистрируй подписки без условия по стороне сети. Если обработчик должен выполнять действие только на сервере, поставь в начале обработчика ранний выход по `_net.IsClient`.
- Каждый ECS-компонент в `Content.Shared` помечай `[NetworkedComponent]`. Для изменяемого состояния, которое должен получать клиент, используй `[AutoGenerateComponentState]` на компоненте и `[AutoNetworkedField]` на соответствующих полях. При ручном изменении такого поля, в том числе содержимого коллекции, вызывай `Dirty` или `DirtyField`. Производный локальный кэш оставляй без `[AutoNetworkedField]`.
- Ставь `[Access(typeof(СистемаВладелец))]` отдельной строкой **после** основных атрибутов компонента. Каждое поле компонента без `[DataField]` помечай `[ViewVariables(VVAccess.ReadWrite)]`. Это относится и к кэшам, и к полям с `[AutoNetworkedField]`.
- Для компонентов и публичных методов пиши XML-документацию на английском. Открывающий тег `/// <summary>`, описание и закрывающий тег `/// </summary>` располагай на отдельных строках.

## Кэш и обработка событий

- Храни кэш конкретной сущности в компоненте этой сущности. Например, каждый рюкзак хранит собственные ссылки на батареи. Система управляет кэшем через этот компонент.
- На частом пути сначала проверяй кэш. Ищи по рукам, слотам и контейнерам при отсутствии записи, несовпадении сущности или устаревшей ссылке. Перед сохранением результата проверь фактическое содержимое нужного слота.
- Сбрасывай запись по событиям, разрывающим связь. Для дозарядки это извлечение или замена батареи, выпадение оружия из рук, снятие рюкзака и удаление компонента механики. Если изменение уже представлено событием, используй его вместо опроса в `Update`.
- В `foreach` используй `continue`, когда следующий элемент ещё может выполнить операцию. Например, после пустого поверпака можно попробовать другой. Используй `return`, когда операция завершена или общее для всех элементов условие уже нарушено, например оружие больше не в руках.

При проверке изменений проследи путь от прототипа до обработчика. Для кэша проверь повторное использование, замену и извлечение цели. После разрыва связи снятый предмет должен перестать получать эффекты механики.
