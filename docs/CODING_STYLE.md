# Стиль C# в TTMC14

Правила применяются к написанию и ревью C# в проектах TTMC14, включая тесты. Настройки форматирования и имён задаёт корневой [.editorconfig](../.editorconfig).

## Размещение кода

- Новый код MC размещайте в `_MC` соответствующего проекта. Общие компоненты, события и логику, исполняемую обеими сторонами, помещайте в `Content.Shared`, серверную реализацию — в `Content.Server`, интерфейс и отрисовку — в `Content.Client`. Для типов MC следуйте принятому в подсистеме префиксу `MC`.
- В ECS компонент хранит состояние, а `EntitySystem` реализует поведение. Название заканчивайте на `Component`, `System` или `Event` по роли. Системы получайте через `[Dependency]`. Обработчики вида `OnEyeShutdown` подключайте через `SubscribeLocalEvent` при инициализации системы. Сигнатуру обработчика согласуйте с контрактом события, включая передачу по `ref`. [Компонент](../Content.Shared/_MC/MarkerEye/Components/MCMarkerEyeComponent.cs) · [Система и подписки](../Content.Shared/_MC/MarkerEye/MCMarkerEyeSystem.cs)
- Общую формулу, проверку или форматирование реализуйте один раз. Операцию одного класса оставьте закрытым методом. При повторном использовании разместите её в модуле, которому принадлежат типы получателя и аргументов. Если вызов естественно читается как действие над получателем, используйте расширение с параметром `this` и делегируйте существующей реализации.

## Оформление и имена

- Файл обычно носит имя основного типа. Сначала идут `using` (начиная с `System` и `System.*`), затем пустая строка и файловое пространство имён по каталогу, например `namespace Content.Shared._MC.MarkerEye;`. При совпадении имён типов явно обозначайте источник.
- Используйте четыре пробела, ориентир в 120 символов и скобки на отдельных строках. У короткого `if` с единственным `return`, `throw` или `continue` скобки допустимо опустить. Отделяйте начальные проверки пустой строкой от основной операции.
- Явно указывайте доступность и тип полей. Для однократно присваиваемых полей используйте `readonly`, для локальных переменных предпочитайте `var`. Если тип задан объявлением, допустимы `new()` и `[]` для пустой коллекции.
- Держите перегрузки рядом. Крупный тип можно разделить по темам на регионы или на `partial`-файлы вида `MCMarkerEyeSystem.Entry.cs`. Поля конкретной части держите при использующих их методах. В длинной сигнатуре переносите каждое `where` на отдельную строку с отступом, ограничения одного параметра перечисляйте через запятую.

| Элемент | Имя |
| --- | --- |
| Тип, пространство имён, свойство, событие, открытое поле | `PascalCase`. Тип называйте по предмету, свойство — по значению |
| Метод, локальная функция | `PascalCase`, действие или принятый предметный термин |
| Интерфейс, параметр типа | `IContract`, `T` или имя роли вроде `TComponent` |
| Закрытое поле экземпляра или изменяемое закрытое статическое поле | `_camelCase` |
| Поле-константа, поле `static readonly` | `PascalCase` |
| Параметр, локальная переменная или константа | `camelCase` |

Имя метода должно читаться вместе с получателем и аргументами. Используйте одну лексику в семействе операций. `Is…` и `Has…` проверяют условие, `Get…` получает ожидаемое значение, `Try…` возвращает `bool` и при поиске передаёт результат через `out` (например, `TryComp`). В `GetOr…` назовите действие при отсутствии значения, в `From…` — исходное представление или единицы, в `As…` — представление результата. Для вариантов `Fast` и `Unsafe` укажите, какая точность или гарантия меняется.

Добавляйте суффикс, когда он уточняет роль. Для утилит и расширений приняты `Helper` и `Extension(s)`, для создания, регистрации и повторной выдачи объектов — `Factory`, `Registry` и `Pool`, для разбора и форматирования — `Parser` и `Formatter`. `Backend` обозначает реализацию поверх библиотеки, `Processor` — обработчик данных. Используйте `Attribute`, `Generator`, `Analyzer` и `Exception` для соответствующих типов C#.

## Управление потоком и контракты

- Предпочитайте ранний `return`, `throw` при нарушении предусловия и `continue` при пропуске элемента. Избегайте `else` и цепочек `else if`. Для двух коротких выражений подходит `?:`, для нескольких вариантов одного значения — `switch`. Проверяйте `null` через `is null` и `is not null`. Запрещены все формы `goto`, включая `goto case` и `goto default`. Для выхода из цикла или секции используйте `break`, общую работу ветвей выносите в метод.
- Свойство представляет значение, метод — действие. Документируйте побочный эффект чтения свойства. Для одного выражения используйте `=>`, для последовательности действий — блок. Перегрузки делегируют основной реализации, конструкторы — через `: this(...)`.
- В сигнатуре `out` обозначает дополнительный результат, `in T` — ссылку для чтения, возврат `ref T` — доступ к месту хранения. Чтобы сохранить ссылку на структуру, используйте `ref var x = ref …`; обычное присваивание копирует значение. Если выходная ссылка определена при успехе, выразите это через `[NotNullWhen(true)] out T? value`.
- `With…` у неизменяемого типа создаёт новое значение, у изменяемого построителя может обновлять его и возвращать `this` или `ref this`. Для непрерывных данных выбирайте `ReadOnlySpan<T>` для чтения и `Span<T>` для записи. Укажите, кому принадлежит память и создаётся ли копия. Если представление позволяет обойти неизменяемость, отразите это в имени и документации.
- Для обычных событий .NET подходят `Action?` или `Action<T>?`, для аргументов — суффикс `Args`, для отдельного делегата с именованными параметрами или `ref` — `Handler`. Давайте парные имена методам подписки и отписки. Снимайте собственные обработчики долгоживущего источника при завершении работы подписчика.
- Используйте `[MethodImpl(MethodImplOptions.AggressiveInlining)]` для обоснованной оптимизации малой операции на горячем пути. У свойства атрибут ставится на аксессор.

## Типы, идентификаторы и интерфейсы

- Для конкретной реализации без точек наследования подходит `sealed class`. Малое неизменяемое значение представляйте через `readonly struct` с допустимыми открытыми полями `readonly`, компактное сообщение с равенством по значениям — через `readonly record struct`. Позиционные параметры, образующие публичные свойства, пишите в `PascalCase`. Для настроек с именованной инициализацией используйте `get; init;`, значения по умолчанию задавайте при объявлении, необязательные ссылки отмечайте `?`.
- Для совместимых признаков используйте `[Flags]` с `None = 0`, отдельным битом на признак и комбинациями через `|`. Неявное преобразование подходит для взаимозаменяемых представлений, при возможной потере данных требуется явное.
- Сохраняйте предметный тип идентификатора в полях, параметрах и ключах коллекций. В RobustToolbox используйте `EntityUid` для локальной сущности, `NetEntity` для её сетевого идентификатора и `EntProtoId` для ID прототипа сущности. `Handle` обозначает дескриптор ресурса.
- Когда строка обозначает имя типа, поля или параметра C#, обязателен `nameof`. Ключи Fluent, ID прототипов и явно заданные имена полей YAML принадлежат формату данных и сохраняют точное написание.
- Интерфейс описывает доступные вызывающему коду операции. В длинном списке интерфейсов оставляйте двоеточие после имени типа и переносите каждый интерфейс на строку с отступом. Обычный API реализуйте публично, дополнительную форму контракта — явно, делегируя общей реализации. Это относится и к статическим членам.

## Документация и тесты

Пишите XML-документацию публичного API на английском. В `<summary>` укажите наблюдаемое поведение и побочные эффекты, в `<returns>` — смысл результата, в `<exception>` — условие ошибки. Для реализации документированного контракта используйте `<inheritdoc/>`. Атрибуты идут между комментарием и объявлением. Для API внешних потребителей библиотеки применим `[PublicAPI]`, для компактного представления значения в отладчике — `[DebuggerDisplay]`.

Называйте тест по проверяемому поведению и следуйте стилю соседних тестов, включая использование подчёркиваний. Модульные тесты находятся в `Content.Tests`, интеграционные — в `Content.IntegrationTests`. В NUnit используйте `[Test]` для одиночного сценария и `[TestCaseSource(nameof(...))]` для общего сценария с источником данных.
